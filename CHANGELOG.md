# Changelog

All notable changes to the SeanPak utility are documented in this file. (3.0.0 was published under the product's former name, CrucibleKit; releases before 3.0.0 under its original name, RustPak.)

## [5.1.0] - 2026-11-13
### Added — per-user install locations (token paths)
- **A package can now say "the per-user Programs folder" — and that is the default.** `installLocation` accepts token paths in the same grammar `dataDirs` already used: a path starting with `%LOCALAPPDATA%`, `%APPDATA%`, or `%USERPROFILE%` resolves on the installing account at install time. When a manifest records no location, the package now records `%LOCALAPPDATA%\Programs\<App>` — `C:\Program Files\<App>` is never a SeanPak default again (it is what put ai.md's 0.7.0 in Program Files). `validate`, `pack`, `init`, `schema`, and the Builder all teach and accept the token form; `%INSTALLDIR%` is refused with its own plain error (a location cannot be defined in terms of itself), as are relative paths and token roots with nothing below them. Existing packages that name an absolute path explicitly behave exactly as before — the recorded folder is honored as written, and the 4.8.0 elevation offer still covers an unwritable one.
- **What the user sees is the real folder.** The wizard's default location is the resolved absolute path (the token resolved for this account), answer files' locations resolve the same way, the headless `--to` value resolves through the same code, and the Builder's Options page note shows the recorded token plus where it lands on this PC.

### Changed — installers created from now on default to a desktop icon and launch after setup
- **Creation defaults, applied only where a manifest is silent.** A manifest that omits `desktopShortcut` already defaulted it on; now a manifest that omits `launchAfterInstall` likewise records it as offered and ticked by default, the `seanpak init` template writes both defaults explicitly, and a new Builder project starts with both on. A manifest that sets either field explicitly — including `false` — is never overridden, and installers built before this change behave exactly as they did.

### Added — silent auto-update
- **Re-running a Setup for an app that is already installed just updates it.** When the wizard starts and the install receipt at the package's target location names the same app at an older or the same version, the page flow never opens: a minimal window ("<App> Setup", "Updating <App>…", one progress bar, no buttons) runs the ordinary upgrade-in-place through the shared install operation — journal, rollback, shortcuts, and receipt semantics are the install operation's own, so a failed update rolls back and shows the plain-English error in that window; an update is never a silent failure. On success it reads "Updated to <version>.", offers one **Close** button, and closes itself after about five seconds. A newer installed version is not an update: the normal wizard opens and its existing downgrade refusal stands. First installs, a receipt for a different app, and an install recorded at a different folder all get the normal wizard, unchanged. Headless `--install` semantics are unchanged; its success report gains an `"action"` field — `"update"` when an existing install was updated, `"install"` for a fresh one.
- **If the program is running, it is asked to close — once.** The update first finds the processes whose executable lives in the install folder and asks their windows to close (a normal close request, so the app keeps its own save prompts), then waits a few seconds. If they close, the update proceeds, and after a successful update the app's main program is relaunched if it had been running. If any process refuses, the flow makes its one permitted interruption: "<App> is still running." with **Close it and update** (the installer ends the program and continues) and **Cancel** (nothing is changed). The decision — receipt state and version comparison to first run / silent update / downgrade — is one pure, host-tested function in `src/update.rs`; no new dependencies (process enumeration goes through `K32EnumProcesses` from the already-linked kernel32).

### Known limitations
- The whole Windows side of silent auto-update is **Unverified** on a real Windows desktop: the minimal window's rendering, finding the running program's processes, the close request and the wait, the still-running choice (both buttons), ending a refusing program, the relaunch after updating, and the success auto-close timing. The decision function, the folder matching, the token resolution, and the absent-vs-explicit-false defaulting are covered by host tests; the window and process shell is compile-verified on the Windows target only.
- Token install locations are **Unverified** end-to-end on a real desktop (resolution is host-tested against synthetic roots); a package recording a token path installs with the same code path as an absolute one once resolved.

## [5.0.0] - 2026-11-13
### Redesigned — the Builder is now a guided page flow (approved mockups; the major version is the window replacement)
- **Pages, not panes.** The Builder studio's single dense IDE window (Design H) is replaced by the flow SEAN approved from mockups on 2026-11-13: a left navigation rail (Home, Projects, Build, Settings) and one page per job. **Home** welcomes with a **+ New Project** button and the recent projects list. **Projects** is the full list, with Open and Remove from list. **New Project** is a three-step rail — Project Details → Program Folder → Summary — that creates the project and lands in the editor. The editor keeps three tabs: **Files and Folders**, **Installer Options**, and **Program Requirements**. **Build Settings** holds the build and the package checks, **Building** runs the build with a progress bar and a timestamped log, and **Build Finished** reports the result — success with the summary and **Open the Installer** / **Open Folder** / **Build Another**, or failure with the plain-English reason and a way back, never a dead end. The installer wizard and the CLI/AI surface are unchanged.
- **Recent projects.** Projects the Builder opens or saves are remembered (name, version, when last touched) in the Builder's own settings file (`seanpak-studio.json` beside the exe — the same store that already kept window geometry and last-used paths; no registry writes for Builder state). Clicking one reopens it in the editor; the Settings page manages the list (including Clear the list) and shows the diagnostics log location, the settings-file location, and the version.
- **Everything the 4.7.2 studio could do is still here.** Program Folder… and the folder scan; the files table with Destination column, packed-size estimates, and the include checkboxes in the folder listing; Remove selected; totals; open / save / save-as; Check details; Verify package, Also test-install, and Test install; the Advanced options (JSON) power-blocks editor (now on Installer Options); the manifest-format (schema) printout (now from Installer Options into the Build page console); Open output folder; Preview installer (same behavior, same words); cancellable jobs with the footer Cancel button and Esc; the subclass-painted dark list headers; full-path tooltips and a plain tooltip on every main control. The tested document/settings/scan model underneath is the 4.x model — the window layer was rebuilt around it.
- **Themed directly on VS Code GitHub Dark High Contrast.** Per SEAN's ruling for this redesign, the Builder uses that theme as drawn in the approved mockups — the same GitHub Dark High Contrast values the shared `src/theme.rs` already carries, now laid out as the mockups' pages. The wizard keeps its Design E (Rail) layout and the same tokens.

### Shown honestly, not faked — where the mockups met the real manifest
- **Program Requirements is a display, not an engine.** The Windows row shows the current floor ("Requires Windows 10 or later", tagged **Built in**, ticked and not editable): no manifest field exists for a minimum Windows version and none was invented, and nothing enforces it yet. The runtime rows (.NET Framework, .NET 8 Desktop Runtime, Visual C++ Redistributable, WebView2) are greyed and tagged **Coming later**, with the page's note saying so — there is no prerequisites engine in 5.0.0.
- **Compression is shown as always on.** SeanPak already compresses every file automatically (storing it uncompressed when compression would not shrink it); there is no on/off setting to wire, so Build Settings shows the ticked, labelled state rather than a switch that does nothing.
- **The program icon is the built-in SeanPak icon.** Manifests have no icon field and none was invented; Installer Options says so plainly ("Built-in SeanPak icon — custom program icons are not supported yet"). Architecture stays **x64 only**, shown as a fact, not a choice.
- **The Options page preview is a sketch.** A static panel draws the wizard's first page with the project's name; the real thing is one click away via Preview installer, unchanged from 4.7.2.

### Known limitations
- All 5.0.0 Builder rendering and interaction is **Unverified** on a real Windows desktop: the page layouts at real sizes and DPI scalings, the nav/tab owner-draw, the New Project step rail painting, the include-checkbox listing, the progress-bar colors, and the Build Finished badge. Host tests cover the document/settings model and every shared operation (unchanged from 4.8.0); the window layer is compile-verified on the Windows target only. Screenshots are owed from the next field pass, not faked.

## [4.8.0] - 2026-11-13
### Added — the elevation offer (SEAN's pick: hybrid; per-user stays the default)
- **Restart as administrator, offered at the wall — never demanded, never silent.** SeanPak still installs per-user and its manifest still says `asInvoker`: nothing requests administrator rights on its own. What changed is the one dead end a per-user installer could not climb — a chosen folder this account cannot write (the classic `C:\Program Files` default some packages record). When the writability verdict fails and this process is not elevated, the wizard's Review page now offers **Restart as administrator** beside the existing **Use per-user folder** remedy — the per-user folder stays the recommended path, and the offer says in plain words what restarting means: Windows will ask for permission, and the install will then run as the administrator account it elevates with, so its shortcuts and settings belong to that account. Install stays disabled until the location is writable, exactly as before, and picking the per-user folder works exactly as it did in 4.3.0.
- **The hand-off preserves what the user already chose.** The restart relaunches this same executable elevated (the `runas` verb; Windows shows the UAC prompt) with the original arguments preserved — bare wizard, `--modify`, an applied preset's answer file — plus the install location currently chosen, so the elevated instance opens on the folder the user actually picked, with an applied preset already applied. This window closes only after a successful hand-off. If the user declines the UAC prompt, the wizard stays open, notes it in plain words on the status line, and the per-user offer stays intact — no error page. The Modify wizard gets the same offer on the same terms.
- **The uninstall confirmation gets the same offer.** When the folder an app lives in is not writable by this account, the confirmation window shows the note and the **Restart as administrator** button; a successful hand-off leaves this process having removed nothing, and the elevated copy runs the whole confirmation again under the administrator token.
- **Headless parity, behind an explicit flag only.** The `--json` refusal for `location_not_writable` (install and modify, dry runs included) gains `"elevationOffered": true` — the field is omitted entirely when the location is writable. Self-elevation from the command line happens only with a new `--elevate` flag on `--install` / `--modify` / `--uninstall`: the same command relaunches elevated, the parent waits for it and returns its exit code. Without `--elevate`, headless behavior and exit codes are unchanged (the writability refusal is still exit 5).
- **A loop guard, by construction.** A relaunched instance carries an internal `--elevated-relaunch` marker; an instance that has the marker (or is already elevated) and *still* finds the location unwritable never re-offers the restart — it refuses plainly with the existing report. The decision (proceed / offer / refuse from verdict + token elevation + marker) is one pure function in `src/elevation.rs`, shared by every surface and unit-tested off-Windows; elevation is read from the process token, and no manifest setting changed.

### Known limitations
- The whole elevation flow is **Unverified** on a real Windows desktop: the UAC prompt and hand-off, the elevated wizard opening on the carried location/preset, the declined-prompt note, the uninstall confirmation's restart, and the `--elevate` wait/exit-code propagation are covered by the host unit tests for the decision and argument construction only — ShellExecute and the token check cannot run on this build host. The per-user default flow (including the 4.3.0 one-click fallback) is behavior-identical to 4.7.2 and needs no re-verification beyond the standing field pass.

## [4.7.2] - 2026-11-13
### Fixed — Builder studio field fixes from SEAN's 4.7.1 run

The owner-draw path is deleted. Applied to the studio's files table and the wizard's Review list, which shared the identical defect; wizard behavior is otherwise untouched.

The table's fixed columns are sized so every header label (File / Destination / Size / Packed (est.)) fits whole at the default window size, with the vertical scrollbar's width reserved so the last column is no longer clipped by it. The Program folder and Output folder fields carry tooltips with the FULL current path, updated whenever the path changes, so a clipped path is always readable.

They and their copy helpers are removed. One **Program Folder…** button (plus Project → **Choose Program Folder…**, plus the PACKAGE row's Browse… button) runs the one flow: pick the folder your built program is in → it is set → scanned → the table, listing, and totals fill. The Remove button is now **Remove selected**. Files a manifest already lists beyond the folder scan still display (marked missing) and remain removable, exactly as before.
- **Labels in plain English.** APP MANIFEST → **PROGRAM DETAILS**; "Primary exe" → **Main program file**; "Power blocks" → **Advanced options (JSON)**; the Sandbox checkbox → **Also test-install**; both Validate buttons → **Check details**; Verify → **Verify package**; "Files folder" → **Program folder**; the bare "…" browse buttons → **Browse…** (visible words, wider buttons — a bare ellipsis is neither plain English nor a usable accessible name). Every renamed control keeps its caption as its window text, so accessible names match the labels.

### Added — cancellable operations, Open output folder, Preview installer
- **Every long studio operation can be cancelled.** The shared operations gained opt-in progress + cancellation hooks in the codebase's existing style (`BuildControl` beside extraction's `ExtractControl`; `pack_with_hooks`, `verify_package_with`, `sandbox_verify_with`, `ScannedFolder::scan_with`, `scan_package_with` — the CLI passes no hooks, so CLI behavior and JSON are byte-identical). Cancellation is checked between files in the folder scan, the overlay build, the portable zip, and the verify decode, and between phases in the sandbox test install (a subprocess already running runs to completion — killing it would leave its sandbox in an unknown state). The studio's footer gains an owner-drawn **Cancel** button, enabled only while a job runs; while a job runs the other action buttons are disabled, the status line names the operation ("Building Setup… (Cancel stops it)") with file counts when the operation reports them, and Esc cancels too. A cancelled pack removes any of the three release files the run itself placed and never touches files that existed before the run (the pack builds into a temp folder and snapshots which outputs pre-exist), reporting "Build cancelled — the unfinished files were removed." A cancelled scan keeps the previous folder contents on screen. Every job ending — success, failure, cancel — restores the controls.
- **Open output folder** (footer): opens Windows Explorer at the output folder, selecting the built Setup file in it when present (`explorer.exe /select`), falling back to the folder itself; enabled whenever an output folder is set. A not-yet-created output folder is explained, not errored.
- **Preview installer** (footer + Build menu): there is no view switch to find — the same program opens the Builder when it carries no package and the installer wizard when it IS a built Setup file — so this launches the current project's built Setup file (`<App>-v<ver>-x64-Setup.exe` in the output folder) and the real wizard opens, with the status line saying so plainly: "Opened the installer preview — this is what people see when they run your Setup file. Nothing is installed unless they click Install." With nothing built yet it says what to do instead: "No Setup file yet. Click Build Setup first, then Preview installer to see what people will see."

## [4.7.0] - 2026-11-13
### Added — the Power bundle, surface slice (the Power bundle is COMPLETE)
- **Modify mode.** An existing install can be changed in place through one shared operation (`src/modify.rs`) behind three doors: the CLI (`--modify [--to <dir>]`, with the same option/component flags as install, `--dry-run` plans, and JSON in/out), the wizard re-opened in Modify mode (a bare interactive `--modify`, or the new ARP **Modify** button — the uninstall entry now carries a `ModifyPath` and no longer sets `NoModify`), and any pre-4.7.0 install gains its ModifyPath the first time a 4.7.0 modify runs. The wizard seeds its pages from the install's receipt — current options, component selection, login entry — with the location fixed. Applying reconciles: files of newly selected components are extracted, deselected components' files are deleted, the system artifacts are removed and re-applied per the new choices, the journaled writes are re-applied, and the receipt is rewritten (`mode: "modify"`). Before anything changes, the rollback journal snapshots the receipt and every file the reconcile will delete or overwrite; any failure — or a cancel — restores the pre-modify state and re-applies its artifacts. Modify runs no install hooks (hooks belong to the install event; a repair runs the post phase). A destination with no SeanPak receipt is refused in plain words ("nothing to modify"), exit 5.
- **Answer files.** `--install --answers <file.json>` presets an install: `installLocation`, `desktopShortcut`, `startMenuShortcut`, `startMenuFolder`, `fileAssociations`, `pathEntry`, `startAtLogin`, `launchAfterInstall`, `components`, `withoutComponents`, and `purgeDataOnUninstall`. Priority is explicit flags > answer file > package defaults. The format is strict on purpose: unknown fields are errors, every validation message names the field, and a malformed file is a usage error (exit 2). `seanpak answers-template <Setup.exe>` prints a template with the package's defaults (including the resolved component selection) filled in. The wizard offers an `answers.json` found beside the Setup.exe on its Review page — **Apply preset / Ignore**, never applied silently; an invalid beside-exe file is explained on the page and not used. `purgeDataOnUninstall` is recorded in the receipt (`purgeDataDefault`): the interactive uninstall confirmation's data-purge checkbox *starts* in that state — the user still decides in the window, and a silent uninstall still never purges without `--purge-data`.
- **`inspect` + `diff`.** `seanpak inspect <Setup.exe> [--json]` reports a package: identity, the options block, components with packed sizes, hooks, registry/environment writes, rich shortcuts, and the per-file list with sizes, stored sizes, compression codec, and owning component. `seanpak diff <A> <B> [--json]` compares two packages: files added / removed / changed (by SHA-256 of the payload bytes), identity and option deltas, and power-block deltas in plain language. **New exit code 6 = differences found** (0 = identical, 3 = a package could not be read), documented in `--help`, the README, and `docs/PARITY.md`.
- **`seanpak init`.** `seanpak init <dir> [--name <App>] [--force] [--json]` scaffolds a project folder: a starter `manifest.json` (primary executable detected from the folder — or its `files` subfolder, which init then treats as the payload folder — app name from `--name` or the folder, version 1.0.0) with the five power blocks present as **inert examples** (an example component claiming no files and not selected by default; empty hook/write/shortcut lists), plus a `PACKAGING.md` stub carrying the one pack command for the detected layout, the verify lines, and worked power-block examples. The generated manifest is validated with the real manifest parser before anything is written, and an existing manifest (or PACKAGING.md) is never overwritten without `--force` (refusal is exit 4, the pack shape).
- **Builder studio: Power blocks editor.** The IDE manifest pane gains a multiline JSON editor for the whole power object — one editor for all five blocks (components, hooks, registryWrites, envWrites, shortcuts), because the blocks are heterogeneous and five structured mini-editors would not fit the pane; the JSON is the same encoding the manifest file and the package block use, parsed by the same strict reader (unknown keys are errors). Fill shows the document's blocks pretty-printed; harvest parses back into the manifest model with the usual dirty tracking. Invalid JSON keeps the previous model and reports the error to the output strip (once per distinct error). This closes the 4.6.0 note that the pane fields land in the next slice.

### Known limitations
- All new Windows runtime behavior is **Unverified** until SEAN's field pass: the Modify wizard's rendering and receipt-seeded pages, the ARP Modify button appearing and launching `--modify`, the Review page's answers offer, the uninstall confirmation's preset-starting checkbox, and the studio's Power blocks editor at real DPI. The modify operation's full cycle (install → add component → flip option → remove component), the answers parser and template, inspect/diff against real packages, and init's generated-manifest validity are covered by host unit tests and a host CLI smoke (init → pack → inspect → diff → install → headless modify → answers install).
- Modify reconciles against the package the running Setup.exe carries: modifying with an older/newer Setup.exe of the same app reconciles the install to that package's files and version (this is also the upgrade-by-modify route); the receipt records `previousVersion` when the version changes.

## [4.6.0] - 2026-11-13
### Added — the Power bundle, engine slice
- **Optional components (overlay manifest v6).** A manifest may declare `components`: named parts of the package (`{id, name, description?, files, required?, defaultSelected?}`); files no component claims form an implicit required part named `core`. The v6 overlay block records each component's files and its packed size (computed by the packer with its own codec). Installs extract only the selected components — required parts and the primary executable's part are always in. The wizard's Options page gains one checkbox per optional component (label: name + packed size), the Review ledger reports "N of M parts" and lists required parts as informational rows, and the CLI takes `--components <id,id>` (explicit full selection) and `--without <id,id>`. Upgrades default to the previous install's selection (brand-new components take their manifest default). The receipt records the installed component ids, and uninstall removes exactly those components' files. Dry-run, install, and pack JSON all report the parts with their packed sizes. Readers keep accepting v2–v5 and legacy-magic packages (everything reads as `core`).
- **Pre/post install hooks.** Manifest `hooks`: `{preInstall: [hook], postInstall: [hook]}`, a hook being `{command, args?, onFailure: "abort" | "continue"}` (default abort). Pre-install hooks run after the writability verdict and before any file changes, from the installer's own folder; post-install hooks run after files, shortcuts, and writes are applied, from the install folder, before the receipt is written. Hooks receive `SEANPAK_INSTALL_DIR`, `SEANPAK_APP_NAME`, and `SEANPAK_APP_VERSION` in their environment. An abort failure fails the install and rolls SeanPak's changes back (exit 5); the failed hook and its exit code appear in the report, and every run — phase, command, exit code, policy, outcome — is recorded in the receipt and `seanpak.log`. A continue failure is a recorded warning. A repair run executes only the post-install phase. Dry runs list planned hooks without running them. Uninstall hooks do not exist yet.
- **Journaled registry + environment writes.** Manifest `registryWrites` (`{key, name, type: "sz" | "dword", value}` — keys are relative to HKEY_CURRENT_USER; the validator refuses hive prefixes, absolute hives, and `..` escapes) and `envWrites` (`{name, value}` for `HKCU\Environment`, with the same change broadcast PATH uses). The install captures each write's prior state — value and type, or "absent", plus whether the key itself was created — into the receipt journal, and uninstall restores the priors exactly (values that were absent are deleted; a key the install created is deleted again when it is empty). A pre-existing value of a type SeanPak does not model refuses the install rather than risking data it cannot restore. The wizard Review ledger summarizes the writes as count rows; dry runs list them.
- **Rich shortcuts.** Manifest `shortcuts`: `{name, target, arguments?, icon?, iconIndex?, description?, location: "desktop" | "startMenu" | "both", pin?}` — extra `.lnk` files planned alongside the automatic shortcuts through the same COM path, now carrying arguments, icon + icon index, and description. Targets and icons must be packaged files, and a shortcut is created only when its target's component is being installed. `pin: true` makes a best-effort attempt to pin the shortcut to the taskbar via the shell verb: the outcome (`pinned` / `unavailable`) is recorded in the receipt and the log and never fails the install. Uninstall deletes the link files like every shortcut.

### Plainly stated
