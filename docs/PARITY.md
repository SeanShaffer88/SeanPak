# SeanPak — Parity / Feature Status

Status of the SeanPak plan (Wave 1 native engine v2 + suite contract)
against what the code actually does today. "Shipped" means present in the
tree and covered by the local gate; Windows runtime behavior stays
Unverified until SEAN's field pass (see QUALITY.md).

## AI control — GUI vs CLI parity

SeanPak's primary user is SEAN's AI packaging his programs for release, so
the headless pipeline is the main workflow and the Builder GUI is
secondary. Every capability is a command first; the GUI surfaces are views
over the same shared operations. Every command supports `--json`
machine-readable output, exit codes are deterministic (0 success,
1 generic/GUI failure, 2 usage, 3 bad manifest/overlay, 4 I/O,
5 install failure, 6 differences found — `diff` only, new in 4.7.0), and
build/install operations append JSON-lines records to `seanpak.log`.

| Capability | Shared operation | GUI surface | CLI surface |
|---|---|---|---|
| Pack a release set (Setup.exe + Portable.zip + SHA256SUMS.txt) from a JSON manifest | `pack::pack` | Studio **Build Setup** button on the Build Settings page (worker thread; the Building page shows progress; a refused overwrite becomes an explicit confirm + forced retry) | `pack <manifest.json> <files-dir> [--out-dir] [--force] [--json]` |
| Prove a built installer (overlay, manifest sanity, payloads) | `pack::verify_package` | Studio **Verify package** button (Build Settings page) | `verify <Setup.exe> [--json]` |
| Sandbox-proof a built installer (install → compare → uninstall → residue) | `pack::sandbox_verify` | Studio **Test install** button, or Verify package with the **Also test-install** toggle on (Build Settings page) | `verify <Setup.exe> --sandbox [--json]` |
| Print the manifest JSON Schema | `manifest::MANIFEST_SCHEMA_JSON` | Studio **Manifest format…** button on the Installer Options page (prints into the Build page's output console) | `schema` |
| Validate a manifest | `manifest::AppManifest::from_json` | Studio **Check details** button (editor toolbar + Build Settings page) over the same editor fields and rules | `validate <manifest.json> [--json]` |
| Build a native overlay installer from a folder | `overlay::OverlayWriter` | — (the studio packs via `pack::pack`) | `--batch <folder> --out <exe> [--json]` |
| Generate Inno/NSIS scripts | `backends` | — | `--batch ... --engine inno\|nsis [--script-only]` |
| Install (extract + Uninstall.exe + uninstall entry + shortcuts/associations/PATH/login entry, rollback on failure) | `install::perform_install_with` | Wizard Install button (Options page edits the same options first, incl. the start-at-login toggle when offered) | `--install [--to] [--dry-run] [--repair] [--force] [--start-at-login\|--no-start-at-login] [--json] [--silent\|--headless]` |
| Launch the installed app after install | `install::launch_program` | Wizard Finish-page "Launch <App>" checkbox (offered/defaulted per the manifest) | `--install --launch` (explicit opt-in; JSON reports requested/performed/error) |
| Preview an install without changing anything | `install::plan_install` | Wizard review table (Design E Rail) | `--install --dry-run [--json]` |
| Check the install location is writable (per-user pre-flight; refuses before any change with the `location_not_writable` reason + per-user suggestion) | `install::location_verdict` / `ensure_location_writable` | Wizard Review row marker + **Use per-user folder** one-click action; Options page re-checks as the location is edited; Install disabled while unwritable | `--install --dry-run` reports `locationWritable` + `suggestedLocation`; a real `--install` into an unwritable destination exits 5 with the same reason and suggestion |
| Restart as administrator when the location is unwritable (the user-invoked exception to per-user-only; never offered silently, never the default) | `elevation::decide_elevation` / `relaunch_elevated` | Wizard Review page **Restart as administrator** button beside Use per-user folder (install + Modify modes); uninstall confirmation shows the same button with its note; declined prompt = the window stays open with a plain note | `--install` / `--modify` / `--uninstall --elevate` relaunches the same command elevated, waits, and returns its exit code; the refusal/dry-run JSON reports `elevationOffered`; a relaunched instance (marker `--elevated-relaunch`) never re-offers |
| Review / edit install options before installing | overlay `InstallOptions` (manifest v3+) | Wizard review table + Options page | `validate` / `--list [--json]` expose the same fields |
| List overlay contents | `overlay::OverlayReader` | — | `--list <packed.exe> [--json]` |
| Extract overlay contents | `overlay::OverlayReader` | — | `--extract <packed.exe> --to <dir> [--json]` |
| Uninstall (payload + journaled artifacts + receipt + ARP cleanup; optional data purge) | `uninstall::perform_uninstall` | ARP / `Uninstall.exe` — interactive runs open the confirmation window with the data checkbox first | `--uninstall [--to] [--purge-data] [--json]` (silent runs never purge without the flag) |
| Modify an existing install (components + option choices reconciled; snapshot/rollback) | `modify::perform_modify` / `modify::plan_modify` | Wizard Modify mode (bare interactive `--modify`, or the ARP **Modify** button) — pages seeded from the receipt | `--modify [--to] [--dry-run] [--components\|--without] [--start-at-login\|--no-start-at-login] [--desktop-shortcut\|--no-desktop-shortcut] [--start-menu-shortcut\|--no-start-menu-shortcut] [--path-entry\|--no-path-entry] [--file-associations] [--json]` |
| Preset an install from an answer file | `answers::Answers` (+ `answers::answers_template`) | Wizard Review page offer for a beside-the-exe `answers.json` (Apply preset / Ignore) | `--install --answers <file.json>`; `answers-template <Setup.exe> [--json]` prints the template |
| Inspect a package (identity, options, components, hooks, writes, shortcuts, files) | `inspect::inspect_package` | — (the studio's manifest pane shows the same blocks for a manifest being authored) | `inspect <Setup.exe> [--json]` |
| Compare two packages | `inspect::diff_packages` | — | `diff <A.exe> <B.exe> [--json]` (exit 0 identical / 6 different / 3 unreadable) |
| Scaffold a project (starter manifest + PACKAGING.md) | `init::init_project` | — | `init <dir> [--name <App>] [--force] [--json]` |
| Edit the power blocks while authoring | `PowerSpec` JSON model (`manifest::power_spec_from_json`) | Studio Installer Options page **Advanced options (JSON)** editor | Edit the manifest file; `validate` checks it with the same parser |

GUI-only capability: none. The studio adds input conveniences over the
same operations — picking folders with the native dialogs, editing the
manifest fields interactively, and curating the
package file list, which is exactly the manifest's `files` field (an
empty list when the package is the whole folder, as with the CLI). Its
window geometry/path persistence and recent-projects list
(`seanpak-studio.json` beside the exe)
are a UI preference store, not a capability. No build, install,
verification, or uninstall capability exists only in the GUI.
